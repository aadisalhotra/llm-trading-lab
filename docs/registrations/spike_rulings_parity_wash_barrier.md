## 1. Submission-order parity (registered sequencing rule — rev. 4, 2026-11-08, corrected against `src/execution/barrier.py` at origin `35f4b1c`)

**The operative rule, as implemented in `CycleBarrier._build_plan_locked`** (`barrier.py:131`, `:137–153`) and stated in the module docstring (`:17–22`, quoted): *"Ordering -- among contended intents on that ticker, sell-side ranks before buy-side, and within a side class the book ranks by a deterministic rotation of the participating books, offset by t mod n (t = the registered ordinal tick, n = number of participating books). No randomness; reproducible from (books, t) alone."* The rank key (`:143–144`): `return (0 if not i.is_buy_side else 1, base.index(i.book))`, where `base = submission_order(sorted(self._registered), self._t)` (`:131`) — the rotation runs over **all registered books**, not only the contending ones. **Scope** (`:137–141`): a ticker is contended only when ≥1 book intends a buy-side order (BUY, COVER) and ≥1 other book intends a sell-side order (SELL, SHORT) in the same cycle; a ticker with intents on one side only is uncontended and unaffected. **On a contended ticker, every intent except the winner is held — same-side siblings included — and the held set releases together the instant the winner reaches a terminal state** (`:149–153`: "the cost is a few seconds of latency, never a wash-trade rejection"). The barrier-engaged chain is therefore two segments; the registered chain-time bound stands.

**Parity assessment (registered):** the rule is side-keyed, not book-keyed — every book faces the identical rule, and the wait attaches to the action (buying into an opposing contention), whose incidence varies by book and cycle; no book is a fixed victim. The wait lasts until the seller's terminal state (typically seconds; bounded by the fill deadline). Incidence is behaviour-dependent (a book persistently buy-side in contention waits more often) in the same class as a heavier trader paying more fees — symmetric rule, asymmetric incidence, disclosed per book via `BARRIER_DELAYED`. Within a side class the `t mod n` rotation makes each book first exactly 1/n of cycles (no fixed victim in expectation); for a specific pair the split is (n−g):g, **not pairwise-exact**, and it decides only which of several same-side sellers is the winner versus released seconds later. Admissible under effective parity; the rule matches the within-book sells-first hygiene already registered. A code change mid-window is rejected on the zero-margin validation count; releasing same-side siblings immediately is a Phase C simplification candidate.

**Research corollary:** the barrier engages only on opposing contention, so convergent same-side selection — RQ1's construct — never engages it; RQ1 measurement carries no barrier latency.

**Within each book:** sells-first, unchanged — operational hygiene with its non-economics stated: under T+1 settled-funds enforcement, sells-first confers no same-cycle buying-power advantage (proceeds are unsettled regardless of submission order).

**Corrections recorded (rev. 4):** (a) The 2026-11-04 "code governs" correction (rev. 2–3) was **wrong**: it read the helper `submission_order` (`:70–78`) and not its caller, and registered a rule the code never implemented — per-contention rotation among contending books with pairwise-exact 1:1 alternation. The code rotates over all registered books and ranks sell-side first; the pairwise-exact property does not exist. (b) The original rev. 1 text (fixed permutation, cycle-level rotation) was also not the implemented rule and was never completed. (c) **The probe's `ordering_as_registered: true` verified sells-first only** — `expected_winner()` is hard-coded to the sell side — so it never tested either registered text; an instrument checked against its own assumption (CLAUDE.md rule 9 class). Operations measured the real `CycleBarrier` with five books: the seller went first 10 of 10 in all three opposing pairs tested; same-side intents ranked (n−g):g; same-side siblings held. This rev. 4 text is written from the code and that measurement; the registration corrects toward the implementation, stated as such.

## 2. WASH_REJECT_POST_BARRIER — third Gate 4 (G-EXEC) success class

A wash-trade rejection surviving the barrier is **not** a market constraint (not halt/liquidity/buying-power) — it is an artifact of the registered account structure: two of our books colliding in one account. Classification under the categorical-vs-occasional test: the linkage worked (submitted, venue answered deterministically, terminal state, book reconciled) → **execution-successful**, the rejected intention censored per T2.3. But success must not hide it:

- `WASH_REJECT_POST_BARRIER` is a **distinct enumerated class** in G-EXEC's success taxonomy — *fills/partials; legitimate market rejections; structure-constraint rejections* — disclosed separately, never folded into market rejections. **This amends the committed Gate 4 text as an amendment, not a parallel statement** (the taxonomy stays single-sourced).
- Disclosed descriptor with **registered expectation ≈ 0** — the barrier exists to make this class unreachable, as settled-funds enforcement makes free-riding unreachable.
- **Any nonzero count in the November validation month is a barrier defect and feeds the partition branch-gate.** A nonzero Phase B rate triggers incident review under the forced-change apparatus's incident handling.
- Joins the shared-fate disclosure family: cross-book interference exists because the books share one account; correlated across the colliding pair by construction.

## 3. Cross-book submission barrier (registered execution-environment property)

The barrier changes when each book's orders reach the venue relative to its decision timestamp — an execution-environment property in the settled-funds/fill-deadline class, not an implementation detail.

**Mechanism (corrected rev. 4):** a ticker is contended when ≥1 book intends a buy-side and ≥1 other book a sell-side order in the same cycle (rule 1, `barrier.py:137–141`); uncontended tickers — including tickers where several books intend the same side — submit concurrently and are unaffected. On a contended ticker the winner (sell-side first; within a side, rotation over all registered books by `t mod n`) submits; **every other intent on that ticker is held, same-side siblings included, and all held intents release together the instant the winner reaches a terminal state or its deadline.** Barrier engagement therefore adds one segment to the submission chain, not a cascade (the composition under which the registered fill-deadline feasibility and this registration are jointly satisfied).

**Three composition rules:**
1. **Deadline semantics:** a barrier-held order's fill-deadline clock (the registered fill-time deadline, execution-environment registration) starts at its *actual* submission; the serialization chain must resolve with reconciliation headroom before the next cycle's state build (worst-case chain length bounded; Operations sizes it against the 30-minute cycle; November's chain-time measurement verifies).
2. **Parity:** *who waits* is determined by the §1 rule — sell-side first, then rotation over all registered books by `t mod n`; the wait attaches to the buy side of an opposing contention, whose incidence varies by book and cycle, so no book is a fixed victim; within a side, each book is first 1/n of cycles (not pairwise-exact; disclosed).
3. **Visibility:** barrier-held orders are tagged `BARRIER_DELAYED` in the decision log; the realized cross-book collision rate is a disclosed descriptor. The 7.7% figure registers as the pre-test exposure *bound*, superseded by the measured rate `[CITE-FILL: the RTH test measurement]` — the test refines the number, not the registration.
